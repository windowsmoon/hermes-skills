# Skill Governance 治理原则详解

> 来源：2026-07-20 用户提供的 Skill 治理教程整理
> 核心观点：Agent skills 不是装得越多越好，真正决定稳定性的三个治理动作。

## 为什么装多了 skill 反而变笨？

不是 agent 不会做事，而是太多能力挤在一起以后，它开始选错工具、读错手册、走错流程。每一个 skill 都会增加 agent 的选择空间，选择空间越大，出错空间也越大。

## 原则1：入口治理 — description 写边界，不写能力

### 常见错误

很多人写 skill 的时候，会把描述写得很宽，比如"帮助用户完成内容创作"。因为"内容创作"可以是写公众号、写小红书、写短视频脚本、写技术博客、写投放文案。agent 一看到"帮我写一段内容"，就可能调错 skill。

### 正确写法

- ❌ 不要写：`用于内容创作`
- ✅ 要写：`当用户提供技术主题、目标受众和传播平台，并要求生成技术博客初稿时使用。不要用于短视频脚本、营销海报和客服话术。`

前者是在炫能力，后者是在设入口。

### 理解 Skill 的调用机制

skill 本质上是 agent 可学习的数字资产，是一份操作指南。但这个操作指南不是每次都要塞进 agent 的脑子里，它通常是先暴露名字、描述、路径这些**元信息**，当用户问题真的需要它的时候，agent 再通过工具去读取完整的 skill 文档。

**也就是说，skill 能不能被正确调用，第一步就取决于元信息描述写得准不准。** 如果入口描述很模糊，后面再好的步骤都没用，因为 agent 第一步就选错了门。

### 自测标准

只看 skill 名字和描述，不看正文，也应该能判断什么时候该用它。如果不能，这个 skill 就还没准备好上线。

### Description 标准格式模板

每个 skill 的 description 必须按以下格式书写：

```yaml
description: >
  当 [触发条件1] 且/或 [触发条件2] 时使用。
  用于 [具体任务描述]。
  不要用于 [排除场景1]、[排除场景2]。
  触发词：[触发词1]、[触发词2]、[触发词3]
```

### 重写示例

#### unified-search
```
❌ 当前：统一搜索——一句话同时搜网络和本地 Obsidian 笔记库。
✅ 重写后：
  当用户需要搜索信息，且不确定用什么搜索工具时使用。
  自动路由到最佳搜索源（Tavily/Exa/秘塔/Obsidian）。
  不要用于：仅搜索单一网站、仅搜索本地笔记（走Obsidian RAG）。
  触发词：帮我搜一下、查一下、搜索、找资料、research
```

#### smart-ppt
```
❌ 当前：智能PPT生成 — 5模式路由
✅ 重写后：
  当用户要求生成PPT演示文稿时使用。
  自动路由到最佳引擎（AiPPT/PPT Master/GordenPPT/HTML/ChatPPT）。
  不要用于：Word文档、PDF报告、思维导图。
  触发词：生成PPT、做个PPT、演示文稿、幻灯片
```

#### find-skills
```
❌ 当前：Helps users discover and install agent skills
✅ 重写后：
  当用户想找能完成某个任务的skill时使用。
  搜索skills.sh市场（94万+技能）。
  不要用于：搜索本地已安装的skill（走hermes skills list）。
  触发词：帮我找skill、有没有做XXX的skill、找工具
```

### 触发词概率评估标准

| 触发词类型 | 概率 | 说明 |
|-----------|------|------|
| 精确匹配触发词 | 90-100% | 用户说了完全匹配的触发词 |
| 语义相近触发词 | 60-80% | 用户说了意思相近但措辞不同的话 |
| 模糊匹配 | 20-40% | 用户说了跟skill相关但不直接的话 |
| 不匹配 | 0-5% | 用户的话跟skill无关 |

## 原则2：手册治理 — skill 写成地图，不是百科全书

### 常见错误

一写 skill 就把所有背景知识、所有注意事项、所有案例都塞进去，最后 SKILL.md 变成几千字上万字。对 agent 来说这不是好事，因为 skill 不是教材，是给 agent 执行任务时看的操作手册。

### 正确结构

一个好的 skill 至少要包含四类信息：

1. **输入条件** — 写清楚用户必须提供哪些信息，任务才能开始
2. **执行步骤** — 第一步做什么，第二步做什么，第三步做什么
3. **判断分支** — 写清楚缺资料、目标不清、输出平台不同，这些情况分别怎么处理
4. **失败处理** — 写清楚什么时候要停下来问用户，什么时候不能继续编，什么时候要切换工具

这四类信息比一大堆背景知识更重要。

### 举例对比

**技术博客写作 skill：**
- 糟糕的写法：先讲技术博客的历史，再讲写作方法论，再讲几十种标题技巧，再放一堆案例。agent 读完之后知道很多，但执行时不知道先干什么。
- 更好的写法：如果用户没有提供主题、读者、平台和字数，先补问。如果用户已经提供主题，先拆成三个核心论点，再为每个论点补一个案例，最后生成标题、摘要、正文和结尾。如果主题涉及不确定事实，必须标记为待核实。

### 自测标准

skill 文档读完之后应该能直接进入执行。如果只能让 agent 懂更多，但不能让 agent 做更稳，那它就还不是一个好 skill。

## 原则3：错误治理 — 每次纠错沉淀回 skill

### 常见问题

很多人用 agent 的时候，会不断纠正它。第一次它写错了，你在对话里说"不是这样，应该按这个格式"。第二次它又错了，你再说一遍。第三次它换个场景还是错。

这说明一个问题：你的纠错没有沉淀，只停留在当前对话里，没有进入 skill。

### 核心标准

**agent 可以犯错，但最好只让他犯一次同样的错。**

### 复盘三件事

如果 agent 在一次任务里犯错了，不要只改这一次输出，要复盘：

1. **错误来源** — 入口判断错了？调用了不该调用的 skill？
2. **手册缺口** — 步骤缺失？分支缺失？或者失败处理没写？
3. **规则沉淀** — 把这次错误转成下一次能执行的明确规则

### 沉淀示例

- 当用户要求短视频脚本时，不要调用技术博客 skill
- 当用户没有给目标平台时，先询问平台，不要默认生成公众号文风
- 当资料来源不完整时，输出里必须标注待核实，不要编造确定结论

### 完整机制

```
agent 犯错
  → 复盘三件事（错误来源/手册缺口/规则沉淀）
  → 更新 skill description（加边界）
  → 更新 skill 步骤（加分支处理）
  → 更新 skill 失败处理（加错误场景）
  → 下次任务自动避开已知坑
```

## 总结：从"看起来很聪明"到"真的可交付"

| 阶段 | 特征 |
|------|------|
| **会背手册的助手** | 必须靠你在旁边不断提醒才能用对 skill |
| **接近数字员工** | 能根据任务自动选 skill，按步骤执行，出错后还能把经验沉淀回来 |

### 三个检查项

1. 入口是否清楚？—— description 写边界了吗？
2. 手册能否执行？—— skill 是地图还是百科全书？
3. 错误有没有沉淀？—— 每次纠错回 skill 了吗？

这三个问题答不出来，装再多 skill 最后也只是把 agent 变得更乱。
