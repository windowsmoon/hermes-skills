# 提示词工作流 (Prompt Workflow)

## 核心理念

本 Skill 基于一个关键洞察：**不要在确定 O（目标）之前就动手优化提示词。**

这个洞察来自 Matt Pocock 的 Grill Me 技能（mattpocock/skills），其核心设计是
`disable-model-invocation: true` ——锁定执行权，强制先澄清需求再做任务。

它与你之前在对话中讨论的「人类设 O → AI 理解 why → AI 反馈 → 人类修订 O → AI 执行」
闭环完全一致。`prompt-workflow` 把「理解 why → 反哺 O」这个环节显式化、流程化，
确保每一步都基于深入理解再做下一步。

```
┌──────────────────────────────────────────────────────┐
│  Phase 0: Grill（追问梳理） ← 必须先做               │
│  不急着动手，先穷追猛打问清楚 WHY                    │
├──────────────────────────────────────────────────────┤
│  Phase 1: Optimize（优化）                            │
│  基于 Phase 0 的深层理解，生成优化版提示词            │
├──────────────────────────────────────────────────────┤
│  Phase 2: Iterate（迭代）                             │
│  用户反馈 → 迭代新版 → 直到满意                      │
├──────────────────────────────────────────────────────┤
│  Phase 3: Execute（执行）                             │
│  用户确认后，使用最终版执行任务                       │
└──────────────────────────────────────────────────────┘
```

**为什么必须 Phase 0 先做？**
- 用户给的 prompt 可能方向本身就有偏差（选错了目标）
- 跳过「理解 why」直接优化 = 把一条偏了的路铺得更好，但路还是偏的
- Phase 0 帮你变成结构工程师，而不是铺路工

## 工作流程

### Phase 0: Grill（追问梳理）

当用户丢过来一个 prompt（或需求描述）时，**不要直接开干**。先做 Grill——
像审讯官一样追问清楚真实意图，而不是优化用户给的文字。

**追问清单（按优先级执行）：**

1. **场景问题（必问，至少 1 个）**
   - 这个提示词用在什么场景？Chat 对话 / Agent 系统提示 / 批量生成 / API 调用？
   - 目标用户是谁？最终人类用户 / AI 自身 / 开发调试 / 下游系统？

2. **意图问题（必问，至少 1 个）**
   - 你真正想解决什么**问题**？（不是 prompt 写了什么，是你想达成什么业务效果）
   - 如果这个 prompt 完美工作了，你期望看到什么具体输出？

3. **边界问题（按需问，碰到情况再问）**
   - 有格式/长度/风格约束吗？JSON / Markdown / 纯文本？
   - 有敏感内容/安全限制/不能踩的雷区吗？
   - 之前试过什么版本？踩过什么坑？

4. **上下文问题（按需问）**
   - 这个 prompt 是独立使用还是嵌入在更大的工作流中？
   - 有示例输入/输出可以参考吗？

**Grill 结束条件：** 你能用自己的话清晰复述出用户的真实目标和约束条件，
并且用户确认「对，就是这个意思」。

**边界情况处理：**
- 如果用户说「你先优化吧不用问那么多」→ 尊重用户，不纠缠
- 但在最终交付时加一句提醒：「本次跳过了需求追问环节，如果结果方向不对欢迎让我重新 Grill」

### Phase 1: Optimize（优化）

确认理解后，调用优化引擎生成优化版。

输出格式（严格遵循，不要用自己的话概括）：

```
## 优化后的提示词
[LLM 原始返回的完整提示词 — 不改写、不概括、不重新组织]

## 优化说明
- 改了什么：[具体改动点]
- 为什么改：[每处改动的理由]
- 预期效果：[改动后应该提升什么]
```

**关键规则：**
- 必须展示 LLM 引擎的原始返回，不要用自己的话概括
  - 错误示范：概括了 3 个版本 → 用户问"内容怎么来的？"
  - 正确做法：直接展示 LLM 的完整输出
- 「优化说明」三段式必须完整
- 如果用户问「内容怎么来的」→ 按步骤解释链路：用户输入 → 引擎的 System Prompt → LLM 输出

### Phase 2: Iterate（迭代）

用户给出修改意见时的处理流程：

```
用户: "第二段再改一下，增加技术要求"
Agent: 基于当前版本 + 用户反馈，调用迭代模式生成新版
输出格式同 Phase 1
```

- 每次迭代只根据用户指出的方向调整，不擅自扩写
- 每次迭代保留原始意图
- 用户没说「好了」之前，不进入 Phase 3

### Phase 3: Execute（执行）

用户说「好了」「执行吧」「就这样」——使用最终确认的提示词执行任务。

---

## 三种优化模式

| 模式 | 用途 | 说明 |
|------|------|------|
| `user` | 优化用户侧提示词 | 优化给最终用户的指令 |
| `system` | 优化系统提示词 | 优化 Agent 的系统级指令 |
| `iterate` | 迭代已有版本 | 根据反馈修改当前版本 |

## 技术实现

- 调用 `custom:183399` API（deepseek-v4-flash）作为优化引擎
- 使用专用优化 prompt 模板（角色 + 指令 + 格式 + 示例）
- Phase 0 Grill 是纯对话交互，不需要调用优化引擎

## 输出物保存

优化完成并确认后，最终提示词会：
1. 记录到当前对话上下文
2. 执行任务时直接使用
3. 可选保存到 Obsidian 笔记库

## 常见 Pitfalls（踩坑记录）

1. **跳过 Phase 0 = 方向性返工**：没有理解 WHY 就直接优化文本，
   用户说「方向不对」的时候，不是优化技术的问题，是 Phase 0 没做。

2. **不要用自己的话概括原始输出**：用户要看的是 LLM 实际给了什么，
   不是你的理解版本。概括会丢失关键细节（格式约束、few-shot 示例、结构限制）。

3. **不要在用户没确认之前就执行**：迭代中的版本不是最终版本。

4. **Phase 0 不是万能问，3-5 个关键问题就够了**：不要问烦用户。
   如果用户显式说「直接优化吧」，尊重用户并做标记即可。

5. **Grill 不是找茬，是对齐**：追问是为了确保理解一致，不是为了证明用户错了。
   语气应该是「让我确保理解对你的需求」而不是「你的需求有问题」。
