# 为什么用 Coze 而不是 Hermes Skill

## 用户原话（对话摘要）

> "Coze 的 Agent 能力其实跟 Hermes 是差不多的。但是在复杂且任务场景下或者需要极其稳定的执行流程的规范下，我会把一些我想实现的自动化功能不做成skill（因为skill的调用有概率又有一定的随机性比如写死一个客服回复...，而且很多skill的功能写的太复杂完全在浪费token，我直接扣子工作流作为外挂可以省下很多推理时间和token成本，最后，扣子有很多插件我是不知道API调用的是谁，也不知道它里面有什么数据库支撑，所以不可能完全用hermes复刻扣子插件的功能，只能继续沿用扣子的工作流）"

## 核心原因

| 原因 | 说明 |
|------|------|
| **Skill 调用有随机性** | 同 prompt 可能跑出不同结果，不适合需要稳定输出的场景 |
| **Skill 太复杂浪费 token** | 很多功能写太复杂，token 成本高，不如 Coze 工作流省 |
| **Coze 插件不可复刻** | 不知道 Coze 插件的 API 地址、底层数据库，Hermes 无法复制 |
| **用户已在 Coze 做完思考** | 工作流里已经设计了完整的逻辑，Hermes 只需要取结果 |
| **Coze 执行稳定** | 工作流每次执行结果一致，没有随机性 |

## 使用原则

1. **纯管道模式**：调 Coze API 拿到数据直接返回，Hermes 不加任何推理
2. **不替代 skill**：用户已经在 Coze 里做了完整的思考设计，不需要 Hermes 再分析
3. **省 token**：复杂逻辑在 Coze 跑，比在 Hermes 写复杂的 skill 省 token
4. **插件生态**：未知 API 和数据库的插件只能走 Coze

## 边界条件

**应该用 Coze 的场景：**
- 客服回复、消息处理等需要稳定输出的自动化
- 涉及 Coze 插件的操作（API 未知/数据库未知）
- 多步骤业务工作流（审批、流转、通知）
- 用户已预置在 Coze 中的自动化流程

**不应该用 Coze 的场景：**
- 部署到服务器（scp/ssh，Hermes 自己用 terminal）
- 写代码/造工具（走 OpenCode）
- 查日志/改配置/跑脚本（Hermes 自己用 terminal）
- 简单查询分析（Hermes 自己处理）
